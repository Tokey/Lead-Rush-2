# B60 - HyperMotion and Motion-Matching Research for LR2 Animation

**Status:** implementation started. B60.1 has repeatable CSV/report hooks; B60.8 and B60.9 need runtime integration and review.

## Executive conclusion

HyperMotion should **not** be copied as a proprietary real-time capture or neural animation stack. EA describes
HyperMotion as a pipeline that turns match capture and other motion data into data that a proprietary algorithm
can generate or adapt in real time ([EA FIFA 23 launch](https://news.ea.com/press-releases/press-releases-details/2022/EA-SPORTS-FIFA-23-Delivers-the-Most-Complete-Interactive-Football-Experience-Yet-with-HyperMotion2-Generational-Cross-Play-Womens-Club-Football-and-Both-Mens-and-Womens-FIFA-World-Cups/default.aspx),
[EA FC 24 gameplay deep dive](https://www.ea.com/games/ea-sports-fc/fc-24/news/fc-24-gameplay-deepdive)).
For LR2, the immediately useful EA principles are the public, established motion-matching ideas EA's own team
describes: live pose and trajectory feature matching, category/tag databases, candidate filtering, weighted
cost selection, short query cadences, and inertial blending ([EA GDC talk](https://media.gdcvault.com/gdc2023/Slides/Motion+Matching+at+EA_Delannoy_JC.pdf)).

LR2 already has strong pieces of a hybrid system:

- Kinemation supplies Humanoid clips, FPS action clips, locomotion parameters and playables.
- `SoldierMovement` publishes `MoveX`, `MoveY`, `Velocity`, `Sprinting`, stance booleans and `LocoSpeed`.
- `RetargetProxy` copies the hidden Kinemation pose into the visible SWAT body in Humanoid muscle space.
- `ReloadMotionBridge` applies a clip's helper-bone delta only as calibrated, clamped overlay motion.
- `FirstPersonPoseCheck` measures foot plants, hand distance, reload angle and other visible errors.

The largest existing risk is architectural: LR2 uses deterministic procedural/hand-authored fixes on top of
motion, especially for reload, grip and prone weapon placement. Replacing those systems wholesale would make
visual correctness and gameplay safety less predictable.

## Recommended architecture

Use a **hybrid motion-matching locomotion layer**, not an ML replacement.

1. Keep Kinemation for first-person, reload, weapon equip/unequip and special-action clips.
2. Build a locomotion-only feature database from LR2-owned or licensed clips.
3. Match the character's live pose and a short future trajectory against database frames.
4. Use tags/categories to separate idle, walk, run, start, stop, turn, crouch and prone locomotion.
5. Search only every 4-8 frames, query Burst/jobs if a Unity implementation is needed, and hard-limit candidates.
6. Preserve compulsory actions: reload, jump, mantle, slide and prone entry/exit must buffer and bypass locomotion matching.
7. Keep `RetargetProxy` and the hand/grip/reload bridges as final corrective layers.
8. Add a live telemetry overlay and export a CSV/JSON report for every pose-check run.
9. Ship behind an A/B feature flag and compare against the current clip/state-machine baseline.
10. Revert if it increases pose jumps, foot slide, IK error, CPU/GPU cost or reload overlap.

## Applicable principles

| Principle | LR2 application | Priority |
|---|---|---|
| Live pose features | Search from Humanoid bones after retarget/IK, not merely clip metadata | High |
| Trajectory features | Compare current velocity/facing and predicted 0.25/0.5/1.0 s path | High |
| Pose/trajectory feature weighting | Tune leg feet and pelvis continuity heavily, while preserving aim/weapon intent | High |
| Database tags/categories | Separate gait, stance, direction, start/stop and turn bands | High |
| Search on a cadence | Run at 4-8 frame intervals; preserve the current frame between searches | High |
| Only beat by a meaningful margin | Prevent frame hunting and repeated clips due to tiny cost differences | High |
| Inertial/pose interpolation | Blend transitions instead of hard-cutting and measure max jump | High |
| Compulsory action buffers | Reload and stance/equipment changes override or suspend locomotion selection | High |
| Final corrective layers | Keep HumanPose retargeting, grip offsets, foot IK and reload clamping | High |
| Telemetry-driven tuning | Export query cost, selected clip/frame, match margins and visible errors | High |

## Not applicable or deferred

- **11v11 volumetric match capture:** LR2 has no sports-style full-team broadcast capture pipeline and the data
  would not directly improve first-person rifle handling.
- **A proprietary ML model that creates unseen action clips:** no evidence it is needed, and it would make
  determinism, rollback and cross-review harder.
- **Full automated retargeting as the final authority:** LR2 must continue to enforce hand/grip, weapon-bone,
  muzzle, visibility and clip safety constraints.
- **Physics-optimized retargeting:** interesting for ragdolls, but the current issue is locomotion continuity and
  visible FPS/TP pose correctness, not unconstrained character control.
- **Immediate replacement of all Animator state machines:** too high a regression risk. Prototype one locomotion
  behavior first, leave weapons/actions outside the matcher.

## Acceptance targets

Use measured baselines before implementation:

- Foot slide: no more than 0.02 m/s median and no more than 0.05 m/s 95th percentile for the stance/gait tested.
- Max hand IK residual: no worse than the current verified baseline; per-gun limits belong in the pose report.
- Reload max absolute gun angle: no more than the existing 38-degree safety limit and no new FPS muzzle clipping.
- Hip/ADS camera: no pose discontinuity visible in 1280x720 and 1920x1080 pose captures.
- Selection stability: no more than 10 effective clip changes per 10 seconds in steady forward walk.
- CPU cost: under 0.10 ms average and 0.25 ms p99 on the TestRange bot/player workload, or under the existing
  Unity/GPU frame-budget headroom documented by P3.
- Memory: measured animation database footprint stays under 64 MB per player/weapon rig profile for phase 1.
- QA: every proposed improvement must have a known-bad replay or A/B capture that fails before changes and passes after.

## Subtask implementation order

1. Capture a repeatable baseline.
2. Create a feature schema and database format.
3. Build a synthetic or mocap-backed walk/run database.
4. Implement live trajectory and pose query.
5. Add category/tag filtering.
6. Add inertial/crossfade blending.
7. Protect compulsory actions and weapon overlays.
8. Add telemetry and A/B mode.
9. Run pose/foot/weapon/CPU checks.
10. Cross-review, document and keep a rollback.
